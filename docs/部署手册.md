# 售后 Agent 部署手册

本文是交付入口，涵盖本机复现、容器部署、客户内网离线准备和资源评估。当前已验证 Windows 本机代码与 HTTP 路径；Docker、pgvector 正向、本地模型推理和离线部署尚未实测。下面的离线命令是待目标环境验证的步骤，不是部署验收报告。

## 本机与容器入口

1. 从源码根目录按 [README](../README.md)安装 `requirements.lock`，运行冻结校验和测试。不要重新生成或覆盖 `data/c004-r01/baseline`。
2. 新环境从 `.env.example` 建立私有 `.env`，填写模型、embedding、业务服务和 Demo 身份配置。已有 `.env` 保留，不随仓库或交付包分发。
   知识库路径使用 `KNOWLEDGE_PATH=knowledge`；目录中同时交付 30 篇政策和 `ingest.py`。旧环境若仍指向 `data/c004-r01/baseline/knowledge`，仅更新此路径，保留其他配置。启动和 CLI 入库会核验政策摘要，不能单独更改部署政策而不修订数据契约。
   SQL 路径使用 `DATABASE_PATH=database/ecommerce.db`、`DICTIONARY_PATH=database/dictionary.json`；`database/` 同时包含 `schema.sql`、已装载种子的数据库、字典和 `seed.py`。无需先生成数据。旧环境仅更新这两项路径，保留其他配置；API 启动时核验三份文件与冻结 manifest 的 SHA-256，不一致或出现 SQLite WAL/SHM/journal 附属文件报 `DATABASE_SNAPSHOT_MISMATCH`。`RUNTIME_DIR` 必须在部署数据库目录和冻结数据包之外。
3. 本机演示按 README 启动 Mock 和 Agent。容器服务、入库、健康检查、接口协议与异常处理见[部署与 FAQ](部署与FAQ.md)。
4. 容器目标为 Python 3.12，源码要求最低 3.11；当前本机验证使用 3.14.5。不同解释器版本、OS 与 CPU 架构需要各自安装验证。

## 内网离线安装准备

先确定目标 OS、CPU 架构、Docker/Compose 版本、模型推理服务、模型权重与 embedding 维度。在与目标兼容的联网准备机完成镜像构建、依赖下载和样本校验；将源码、冻结数据、镜像、模型文件与摘要通过获准的介质转入内网。模型权重和推理服务镜像不包含在本仓库内。

### 镜像方式

联网准备机在源码根目录构建同一个应用镜像，供 Agent 和 Mock 使用，并导出向量库镜像：

```powershell
docker build -f docker/Dockerfile -t after-sales-agent:submission .
docker pull pgvector/pgvector:pg17
docker image save -o after-sales-images.tar after-sales-agent:submission pgvector/pgvector:pg17
Get-FileHash after-sales-images.tar -Algorithm SHA256
```

`after-sales-images.tar` 只作为交付介质传输，不应加入 Git。记录实际镜像 ID/digest，不能仅以可变标签代替版本证据。镜像导出使用 Docker 的 [image save](https://docs.docker.com/reference/cli/docker/image/save/)。

内网主机验证介质摘要后导入：

```powershell
docker image load -i after-sales-images.tar
```

导入会恢复镜像及标签，参见 [image load](https://docs.docker.com/reference/cli/docker/image/load/)。在内网源码的 `docker/` 目录创建本地覆盖文件 `docker/docker-compose.offline.yml`，引用已导入的镜像：

```yaml
services:
  api:
    image: after-sales-agent:submission
    pull_policy: never
  business:
    image: after-sales-agent:submission
    pull_policy: never
  vector:
    image: pgvector/pgvector:pg17
    pull_policy: never
```

在私有 `.env` 中把模型和 embedding URL 改为容器可达的内网服务地址，按现有部署说明补齐凭据、向量维度和 Demo 身份。容器内的 `localhost` 指向该容器，不能直接代替其他主机或容器的地址。然后执行：

```powershell
docker compose --env-file .env -f docker/docker-compose.yml -f docker/docker-compose.offline.yml up -d --no-build vector business
docker compose --env-file .env -f docker/docker-compose.yml -f docker/docker-compose.offline.yml run --rm --no-deps --pull never api python -m knowledge.ingest
docker compose --env-file .env -f docker/docker-compose.yml -f docker/docker-compose.offline.yml up -d --no-build api
```

原 Compose 保留 `build` 定义，离线 `up` 显式使用 `--no-build`；入库 `run` 使用已导入镜像、不传 `--build`，并关闭自动启动依赖和拉取。覆盖文件的 [pull_policy](https://docs.docker.com/reference/compose-file/services/#pull_policy) 为 `never`，[run 参数](https://docs.docker.com/reference/cli/docker/compose/run/)中的 `--pull never` 同样禁止拉取。必须先完成入库，随后检查 `/health?mode=ready` 并执行政策、SQL Join、澄清、确认建单、429/500 与写后 UNKNOWN 场景。不能仅以三个容器启动成功验收。

### Python 依赖备用方式

如果采用本机 Python 安装，使用与目标一致的 OS、架构和 Python 版本准备 wheelhouse：

```powershell
python -m pip wheel -r requirements.lock --wheel-dir wheelhouse
```

转入内网后，新建虚拟环境并仅从本地 wheelhouse 安装：

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install --no-index --find-links=wheelhouse -r requirements.lock
.venv\Scripts\python -m pip check
.venv\Scripts\python -m mock.verify_freeze
.venv\Scripts\python -m pytest tests -q
```

`--no-index` 与 `--find-links` 的行为参见 [pip install](https://pip.pypa.io/en/stable/cli/pip_install/)。该步骤只安装 Python 依赖，不能替代 pgvector、模型权重、推理引擎和 embedding 服务的离线准备。当前尚未产出经过验证的 wheelhouse。

## 本地模型兼容性与资源估算

`MODEL_BASE_URL/NAME/API_KEY` 与 `EMBEDDING_BASE_URL/MODEL/API_KEY/DIMENSION` 均可配置。当前 Provider 发送 `chat/completions`、JSON Schema 结构化输出、`enable_thinking=false` 和非流式模型请求；embedding 使用 `embeddings`。目标本地服务需验证这些字段、输出 Schema、向量维度和超时行为，不能仅因宣称 OpenAI 兼容就视为已跑通。

| 项目 | 当前边界 | 估算或验收方法 |
|---|---|---|
| Agent、Mock 与 pgvector | Agent 单 worker；应用本身不加载模型权重 | 记录目标机器 CPU、RAM、磁盘及并发下的 RSS、P95/P99 耗时、错误率 |
| 模型 GPU 数量与显存 | 未选定并实测本地模型，不能给出“几卡几 G 可稳定运行”的结论 | 权重理论字节数约为参数量 × 每参数位数 ÷ 8；总显存还包括 KV cache、计算缓冲、量化元数据、并发与上下文，需实际测量 |
| QPS 上限 | 未压测，不把单案耗时倒数或请求预算当 QPS | 固定模型、上下文、业务混合比例及成功条件，递增并发，记录稳定吞吐和资源峰值 |
| 部署报价 | 未形成客户报价 | 成本项为推理算力、应用与数据库资源、存储备份、监控运维及适配测试；按实测容量和供应商有效报价计算 |

因此，资源规划方法已提供，显存、QPS 和正式报价数值仍是交付待确认项。FAQ、已知风险和失败恢复分别见[部署与 FAQ](部署与FAQ.md)、[风险清单](风险与待确认事项.md)和[交付验证记录](reports/交付验证记录.md)。
